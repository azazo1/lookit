# 根据图片重建 UI 或图形

**何时使用**: 任务是复现图片展示的内容, 比如把页面还原成 HTML, 把图标或示意图还原成 SVG, 或提取可复用的视觉组件. 不用于回答图片问题, 那只需要 `glance`.

工具语法在 `SKILL.md`. 本文件给出完整执行顺序和通过/失败判断.

## 步骤

**1. 先一次盘点, 再按区域细化.**

一次全屏 `detect` 调用得到元素清单. 不要用单个目标调用逐个收集元素, 那样每个元素消耗一次视觉调用, 而一次调用本来就能返回. 全屏扫描在密集页面会漏报, 把它当作脚手架: 对每个布局区块执行 `detect --region` 得到完整局部清单, 再用 `glance --region` 放大, 用 `dominant_colors` 采样颜色.

**2. 观测数字来自像素, 设计几何需要推断.**

精确颜色, 偏移和大小正是视觉模型最容易自信出错的地方. 用代码采样, 或从 `trace` 读取; 它的坐标来自真实像素. 这些数字描述已经栅格化的结果, 不等于原始矢量的控制点或中线. 把测量值当证据, 不要把每个边缘波动都变成 SVG 节点.

**3. 每个形状先决定: 直接交付 trace, 还是只拿它做测量参考.**

有机或不规则形状只有在源图分辨率足够且追踪路径本身平滑时才适合直接交付; 手写近似可能损失细节. 如果输出呈现明显栅格台阶, 仍应把 trace 当测量参考并简化路径. 简单几何 (矩形, 圆形, 圆角块) 或之后还要编辑的 SVG, 把 trace 当作测量参考: 从路径读取位置, 大小和半径, 再手写干净的基础图形.

- **图标/Logo/线条图转 SVG**: `trace --region <ground 框> -o icon.svg`.
- **示意图/流程图/线框图结构**: `--polygon` 会把每个框和箭头变成紧凑路径, 并保留精确位置和大小; 布局关系变成可读文本.
- **测量元素**: 解析追踪路径 (或跳过 SVG 直接在像素上计算), 不要问 `glance` 要数字.

低分辨率图标和线性图标属于手写案例, 不是"不 trace"的案例. 不要用固定图片尺寸判断: 只要一条描边或圆弧仅跨少量像素, 栅格抗锯齿就会显著改变可见边界. trace 返回的是描边周围的带状轮廓, 不是设计中线; 最终产物应使用干净的 `<path stroke=... fill=none>`, `<circle>` 和其他基础图形. 直线保持单一直线, 圆保持圆, 折角斜边保持单一线段.

仍然要用 `trace <icon> --polygon` 测量端点, 角点, 大致描边宽度和相对位置. `ascii` 只适合粗略预览像素结构. 两者都不能证明某个栅格台阶应成为矢量几何. 不要添加碎片路径, 矩形补丁或复杂 mask 来复刻单个边缘像素和抗锯齿.

如果需要让视觉模型直接产出 SVG 草稿, 使用 `model-svg <image> -o draft.svg`. 它适合先获得语义和构图草稿, 不替代后续的几何整理. 对小图标, 检查模型是否使用了平滑基础图形; 如果仍然输出像素台阶, 回到手写 SVG, 不要继续用差异百分比驱动迭代.

复用追踪路径时有两个陷阱:

- SVG 是透明背景; 在做像素差异或视觉检查前先合成白色背景 (`rsvg-convert -b white`); 很多查看器会把透明当黑色, 并误判为 trace 失败.
- 每个 `<path>` 都带 `transform` 属性. 把路径迁移到另一个 SVG 时, 必须连同 `d` 一起复制 `transform`; 孔洞是反向绕向的子路径, 单独提取没问题, 但丢掉 transform 会移动图形.

**4. 颜色值从像素取, 模型只负责命名.**

`glance` 能告诉你某区域看起来是 "浅灰", 但不能确定是 `#F9FAFA`, `#F5F5F5` 还是 `#EDEDED`; 重建页面用错灰色会明显不对, 即使两者都叫 "浅灰". 分三步处理颜色:

1. `glance <image> --region <box> -q "描述这个区域的颜色名称"` - 只拿文字标签; 这一步命名聚类, 不测量.
2. `dominant_colors <image> --region <box>` - 降采样, 量化并合并相近颜色, 输出主要颜色聚类及占比. 直方图是角色图: 占比最大通常是背景, 较小的是强调色.
3. 把每个标签映射到候选调色板, 再让像素选择:
   `dominant_colors <image> --region <box> --candidates '#F9FAFA,#F5F5F5,#F3F3F3,#EDEDED'`
   每个候选色按区域像素距离打分, 最接近者胜出. 重建时使用该十六进制色值.

第 2 步规则仍然成立: 标签来自模型, 色值来自像素.

## 验证

按以下优先级判断重建质量, 前一项不能为了后一项让步:

1. 内容正确: 元素, 文字和整体布局没有缺失或多余.
2. 几何正确: SVG 使用符合设计意图的基础图形, 曲线平滑, 直线干净, 描边一致, 节点数量合理.
3. 栅格接近: 在实际使用尺寸下, 位置, 大小和颜色与参考图接近.

渲染出产物 (HTML 用 Playwright, SVG 用 rsvg-convert). SVG 至少渲染实际使用尺寸和 4 倍检查尺寸. 实际尺寸用于对比参考图; 放大尺寸只检查矢量自身的曲线, 折角, 描边和节点痕迹, 不要把放大的源 PNG 当作矢量几何真值.

先用图模型做一次整体对比:

```bash
glance <原始图.png> <渲染结果.png> -q "对比这两张图, 列出布局, 元素, 文字, 颜色, 间距, 以及缺失或多余的内容"
```

这一步能发现像素差异不直接反映的内容和观感问题; 模型没提到差异不代表没有, 精确位置和大小仍用下面的 `pixel_diff` 定位. 然后:

```bash
pixel_diff <原始图.png> <渲染结果.png> [--region X1,Y1,X2,Y2]
```

它会输出整体差异百分比, 以及最严重区域的 `x1: .., y1: ..` 框; 这些框的格式和 `glance --region`, `detect --region` 相同, 所以最严重的区域可以直接交给放大调用. 传入 `--region` 时只比较该区域, 两张图都会先裁剪到同一范围. 用它定位仍需检查的位置, 大小或颜色, 不要把总百分比当作优化目标.

当一次修改通过增加节点, 台阶, 补丁图形或 mask 来复刻少数像素, 即使 `pixel_diff` 下降也要拒绝. 当内容和几何已经正确时, 允许保留由抗锯齿, 像素对齐或渲染器造成的小幅差异. 简洁, 平滑, 可编辑且能正确缩放的 SVG, 优先于只在单一尺寸上像素差异更低的 SVG.

阅读输出还有两条规则:

- **低百分比不代表只有一个缺陷.** 排序只是从哪里开始看的起点, 不是错误清单. 一个单元格可能同时存在两个问题: 错误填充色很抢眼, 可能掩盖底下的位置偏移. 解释完最严重区域后, 还要检查它是否移动, 缩放或改变形状, 并继续处理后续排名区域直到全部干净.
- **不要用分开的描述对比下结论.** 对原始图和重建图分别生成描述再比较没有意义, 两者来自同一个模型, 盲区会互相抵消; 必须让模型在同一调用里同时看两张图, 精确差异仍由 `pixel_diff` 确认.

脚本会自动把透明合成到白色背景; 如果出于某种原因手动比较, 要自己处理透明.

## 边界

整张截图和照片不适合 trace. 低对比图形 (水印, 浅色图案) 会被二值化掉, trace 反而会拾取周围的高对比内容.

"0 paths" 表示该区域二值化后没有内容, 可以恢复: 依次调高 `--scale`, 收紧 `--region`, 或对浅色背景深色图形先反色. `--color` 最后才用, 而且只用于真正多色图形; 在抗锯齿输入上它会给每个灰度级别单独聚类, 单个图标会变成几十个碎片路径. 这种输出看起来像工具不行, 其实只是用错了参数.
